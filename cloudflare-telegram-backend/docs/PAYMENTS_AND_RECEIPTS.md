# پرداخت‌ها، رسید دیجیتال و درگاه پرداخت (مرحله ۴)

## اصل مهم: رسید موازی وجود ندارد

رسید تلگرامی **همان رکورد پرداخت** است که در تب «پرداخت‌ها»ی اپلیکیشن می‌بینید و همان اطلاعاتی را نشان می‌دهد که دیالوگ «رسید پرداخت الکترونیک» اپ نشان می‌دهد: کد تراکنش، تاریخ و ساعت شمسی، نام هنرجو، شماره قسط و دوره، مبلغ، روش پرداخت، حساب مقصد، کد رهگیری و توضیحات. هیچ دادهٔ ساختگی یا شماره پیگیری جعلی درج نمی‌شود؛ کد رهگیری فقط وقتی نمایش داده می‌شود که واقعاً ثبت شده باشد.

## ۱. ارسال خودکار رسید — فقط تلگرام، فقط بعد از پرداخت واقعی

| قانون | پیاده‌سازی |
|---|---|
| رسید فقط بعد از پرداخت واقعی | رسید از مسیر `/api/sync/payments` ساخته می‌شود که فقط پرداخت‌های ثبت‌شدهٔ اپ را می‌برد؛ قسط پرداخت‌نشده اصلاً ردیف رسید ندارد (تست شده) |
| رسید قسط اول (پرداخت همزمان با ثبت‌نام) | تا امضای قرارداد **نگه داشته می‌شود** (`WAITING_CONTRACT`)؛ فقط بعد از اینکه PDF قرارداد واقعاً به چت هنرجو ارسال شد، با تأخیر قابل‌تنظیم (پیش‌فرض ۱۰ دقیقه) ارسال می‌شود |
| قسط‌های بعدی | بلافاصله بعد از ثبت پرداخت در صف ارسال (`QUEUED`) |
| کارت‌به‌کارت / کارتخوان | ثبت دستی مدیر در اپ → همان مسیر خودکار |
| فقط تلگرام | برای رسید هیچ پیامکی صف نمی‌شود (برخلاف لینک پرداخت یادآوری که زیرساخت پیامک DISABLED دارد) |
| ضد تکرار | کلید اصلی رسید = شناسه پرداخت اپ؛ همگام‌سازی مجدد / retry / تکرار وبهوک هرگز رسید دوباره نمی‌سازد یا نمی‌فرستد |
| پیگیری | وضعیت هر رسید: `PENDING / WAITING_CONTRACT / QUEUED / SENT / FAILED / REVERSED / REVERSAL_QUEUED / REVERSED_NOTIFIED` + تعداد تلاش + آخرین خطا + شناسه پیام تلگرام |
| ارسال مجدد کنترل‌شده | چون هنرجو متصل نبود → رسید در صف می‌ماند و به‌محض اتصال با `/start` ارسال می‌شود؛ خطای شبکه → تلاش بعدی cron (حداکثر ۵ تلاش تا FAILED) |

## ۲. رسید چاپی در «رسیدهای من»

دکمه «🧾 رسیدهای من» در ربات: فهرست متنی رسیدها + **فایل PDF چاپی همان رسیدها** (A4، قالب رسمی، متن فارسی وکتوری بدون فونت، تاریخ شمسی واقعی) تا سقف ۵ رسید آخر. رسیدها فقط از ردیف‌های خودِ هنرجو خوانده می‌شوند (جداسازی مستأجر + هنرجو، تست شده).

## ۳. درگاه پرداخت آنلاین — زیرساخت کامل، هیچ سرویسی فعال نیست

### نتیجهٔ تحقیق «بله‌پی»
سرویسی با نام «بله‌پی» به‌عنوان درگاه مستقل با API مستند عمومی **یافت نشد**. آنچه واقعاً وجود دارد:
- **پیام‌رسان بله (ble.ir)**: API ربات آن سازگار با تلگرام است و پرداخت **کیف پول بله** در ربات (`sendInvoice`) دارد — اما این «درگاه بانکی با تسویه به حساب آموزشگاه» نیست و مستندات پذیرندگی عمومی برای آن یافت نشد.
- کانال‌هایی مثل «درگاه نو» در بله فقط تبلیغ سرویس هستند؛ API مستند قابل‌راستی‌آزمایی ندارند.
- گزینه‌های واقعیِ مستند: **IDPay** (وب‌سرویس v1.1؛ تسویه بدون اینماد ۱۴ تا ۴۵ روز + حق اشتراک)، **PayPing** (API کامل)، **زرین‌پال** (نیازمند احراز پذیرندگی). همه نیاز به ثبت‌نام و کلید دارند — هیچ‌کدام فرض «بدون مدرک» نیست.

**طبق دستور شما هیچ سرویسی انتخاب یا فعال نشد.** زیرساخت مستقل کامل آماده است:

- جدول `payment_transactions`: شناسه یکتای سفارش، مبلغ مورد انتظار (= باقی‌ماندهٔ دقیق همان قسط)، وضعیت (`PENDING/PAID/FAILED/CANCELED/EXPIRED/AMOUNT_MISMATCH`)، مرجع درگاه، payload تأیید.
- لینک اختصاصی `/pay/<token>`: توکن فقط به‌صورت SHA-256 ذخیره می‌شود؛ باز کردن لینک هرگز پرداخت را تأیید نمی‌کند.
- تأیید **فقط سمت سرور** با فراخوانی وب‌سرویس درگاه و مقایسهٔ دقیق مبلغ؛ ادعای کاربر/بازگشت/اسکرین‌شات بی‌اعتبار است.
- پس از تأیید: قسط و تراکنش **خودکار** به‌روز می‌شود + رسید آنلاین در تلگرام ارسال می‌شود + اپ با pull (`/api/payments/confirmed`) همان پرداخت را یک‌بار در Room ثبت می‌کند (idempotent با شناسه سفارش).
- نقطهٔ اتصال سرویس آینده: `registerProviderFactory(id, factory)` در `src/gateway.ts` — یک آداپتور با دو متد (`createPaymentLink`, `verifyPayment`). بدون ثبت آداپتور + کلید، هر لینکی با پیام محترمانهٔ «درگاه متصل نیست» رد می‌شود (۴۰۹).

### تنظیمات مدیر (اپلیکیشن → تنظیمات → درگاه پرداخت و رسیدها)
- شناسه سرویس درگاه (تا تأیید شما خالی = غیرفعال)، شناسه پذیرنده، کلید API (نمایش مخفی).
- تأخیر ارسال رسید قسط اول (دقیقه) + کلید «فقط بعد از قرارداد».
- کلیدها فقط به Worker خودتان (روی HTTPS) می‌روند و هیچ endpoint ای آن‌ها را برنمی‌گرداند.

### روش پرداخت هر قسط
در جزئیات هنرجو، زیر هر قسط پرداخت‌نشده: **آنلاین / کارت‌به‌کارت / کارتخوان**. قسطِ ONLINE در یادآوری تلگرام لینک پرداخت همان مبلغ را می‌گیرد؛ پیامک همان متن در `sms_outbox` با وضعیت `DISABLED` صف می‌شود (ارسال واقعی تا اتصال پنل پیامک خاموش).

## ۴. مهاجرت 0009 (فقط روی شاخه — اجرا نیازمند تأیید شما)

`0009_payments_receipts.sql`: دو جدول جدید + یک ستون (`installments.payment_method`). افزودنی است و مثل 0007 بازسازی جدول ندارد؛ فقط `ALTER TABLE` پایانی غیر-idempotent است (مثل 0001/0003/0004) — فقط یک‌بار از طریق ledger wrangler اجرا شود. این ویژگی روی production قبل از اجرای 0009 فعال نمی‌شود.

## ۵. تست‌ها (همه واقعی و سبز)
