# چک‌لیست انتشار (مرحلهٔ ۹) — وضعیت واقعی هر قابلیت

> تاریخ به‌روزرسانی: ۱۴۰۴/۰۸/۰۳ (2026-10-25). مرحلهٔ ۹ اضافه شد: پنل‌های پیامکی
> (SMS.ir + رایس‌اس‌ام‌اس) و مخفی‌سازی کامل درگاه پرداخت آنلاین. این سند خروجی مرحلهٔ ۸ است:
> «کدام قابلیت آزمایش‌شدهٔ محلی است، کدام نیاز به دسترسی بیرونی دارد و کدام مسدود است» —
> موفقیت تست محلی هرگز با موفقیت عملیاتی سرویس واقعی یکسان نیست.

## ۱. ماتریس وضعیت قابلیت‌ها

| قابلیت | وضعیت | توضیح دقیق |
| --- | --- | --- |
| ربات تلگرام (وب‌هوک، منو، /start، اتصال ربات هر آموزشگاه) | **آزمایش‌شدهٔ محلی** | ۲۰۸ تست Worker سبز؛ شامل fail-closed بودن وب‌هوک (۴۰۳/۴۰۱) |
| پنل پیامکی SMS.ir (لایهٔ مشترک، ارسال، آزمایش اتصال) | **آزمایش‌شده با mock / آمادهٔ ورود کلید** | بر اساس مستندات رسمی sms.ir/rest-api؛ ۱۱ تست قرارداد+خطا+سیاست+ضدتکرار؛ ارسال واقعی تا ورود کلید و اجازهٔ مالک قفل است |
| پنل پیامکی رایس‌اس‌ام‌اس | **مسدود — مستندات عمومی منتشر نشده** | اسلات + فرم آماده؛ آداپتور صادقانه رد می‌کند و هیچ endpoint جعل نشده (جزئیات: SMS_PANELS.md) |
| درگاه پرداخت آنلاین | **مخفی + مسدود (kill-switch)** | `ONLINE_PAYMENTS_ENABLED` پیش‌فرض خاموش: /pay، /api/payments/link، /api/payments/verify و همهٔ اشاره‌های دانشجویی بسته‌اند؛ کارت‌به‌کارت + تأیید مدیر تست‌شده و دست‌نخورده |
| UI اپ: انتخاب پنل پیامکی | **آزمایش‌شدهٔ محلی (Worker) / نیازمند CI (Kotlin)** | تب جدید «د) پنل پیامکی» + masking کلید + آزمایش اتصال؛ گزینهٔ «آنلاین» از انتخاب روش پرداخت حذف شد |
| قرارداد و امضا (صدور، لینک، بازکردن، امضا، PDF، تحویل) | **آزمایش‌شدهٔ محلی** | صفحهٔ عمومی امضا در این مرحله تعمیر شد (تزریق توکن) + escape سراسری؛ تست رندر صفحه اضافه شد |
| پرداخت آنلاین + رسید (لینک، تأیید، صف رسید، برگشت وجه) | **آزمایش‌شدهٔ محلی (درگاه mock)** | گذار PAID حالا CAS است؛ لینک استفادهٔ مجدد URL کامل می‌دهد. **درگاه واقعی هرگز تست نشد** |
| ادعای کارت‌به‌کارت (ثبت، تأیید/رد، تاریخچهٔ رویداد) | **آزمایش‌شدهٔ محلی** | CAS دابل‌کلیک + شناسهٔ قطعی `clm-<id>`؛ escape پیام مدیر |
| یادآوری اقساط (پنج نوبت، دوقانله، توقف/ادامه) | **آزمایش‌شدهٔ محلی** | claim-before-send روی دفتر deliveries + پذیرش سیاست کانال در مسیر خودکار |
| تنظیمات پیام‌رسانی (رویداد/کانال/قالب) | **آزمایش‌شدهٔ محلی** | سیاست `channel: sms` حالا در مسیر خودکار هم رعایت می‌شود؛ «<» تنها در قالب رد می‌شود |
| گزارش مالی و سلامت مالی | **آزمایش‌شدهٔ محلی** | کوئری‌ها academy-scoped؛ تاریخ شمسی الان با روز تقویم تهران |
| پشتیبان‌گیری/بازیابی (مرحلهٔ ۷) | **آزمایش‌شدهٔ محلی** | پوشش ۲۱ جدول شامل کل دفتر مالی؛ صحت‌سنجی قبل از جایگزینی؛ ادامه‌پذیر؛ ۱۶ فراخوانی D1 در برابر سقف ۵۰ |
| تست‌های Android/Kotlin | **نیازمند دسترسی خارجی (CI)** | سندباکس: فقط Java 21 — بدون Gradle/SDK/gradlew؛ هر ۱۰ کلاس تست JVM در `backend-ci` سیم‌کشی شده و باید در CI سبز شود |
| تلگرام واقعی / پیامک / درگاه واقعی / D1 تولیدی | **مسدود به تصمیم مالک** | طبق محدودیت‌های مأموریت فقط mock؛ هیچ پیام واقعی ارسال نشده |

## ۲. پیکربندی موردنیاز پیش از انتشار (الزامی)

| متغیر / Secret | الزام | توضیح |
| --- | --- | --- |
| `API_SECRET_KEY` | الزامی | کلید API همهٔ مسیرهای اپ/قرارداد |
| `WEBHOOK_SECRET` | **الزامی (تغییر این مرحله)** | وب‌هوک حالا **fail-closed** است: بدون این secret (یا `webhook_secret` ردیف آموزشگاه) هر درخواست با ۴۰۳ رد می‌شود. این حفرهٔ «پذیرش آپدیت جعلی» بسته شده است |
| `TELEGRAM_BOT_TOKEN` | Legacy | فقط برای ربات سراسری قدیمی؛ اتصال هر آموزشگاه از `/api/bot/connect` توکن خودش را در D1 ذخیره می‌کند |
| `PUBLIC_BASE_URL` | الزامی برای پرداخت آنلاین | لینک پرداخت در منو/یادآوری فقط با این مقدار (یا origin درخواست وب‌هوک) قابل‌کلیک ساخته می‌شود؛ بدون آن، لینک صادقانه حذف می‌شود (هشدار در لاگ) |
| `ADMIN_CHAT_ID` | توصیه‌شده | fallback مدیر برای ادعاها |
| `BACKUP_RETENTION_DAYS` / `BACKUP_MAX_BYTES` / `BACKUP_INCLUDE_FILES` | اختیاری | پیش‌فرض: ۷ نسخه / ۲۵MB / true |
| `ONLINE_PAYMENTS_ENABLED` | **خاموش بماند** | kill-switch درگاه آنلاین؛ هر مقداری جز `"true"` همهٔ مسیرهای پرداخت آنلاین را مخفی/مسدود نگه می‌دارد. فعال‌سازی بعدی = این پرچم + ثبت آداپتور درگاه در کد + کلیدهای مدیر |
| `SMSIR_API_KEY` (Secret) | اختیاری | اولویت بر مقدار ذخیره‌شدهٔ D1 برای SMS.ir: `wrangler secret put SMSIR_API_KEY` — هرگز لاگ/پاسخ نمی‌شود |

## ۳. مهاجرت‌های محلی (۰۰۰۱ تا ۰۰۱۱)

ترتیب رسمی اجرا فقط از طریق ledger مهاجرت wrangler است
(`npx wrangler d1 migrations apply academy-telegram-db --remote`) — **هیچ فایلی را دستی دوباره اجرا نکنید؛
ALTERهای ۰۰۰۱/۰۰۰۳/۰۰۰۴/۰۰۰۹/۰۰۱۰ idempotent نیستند.**

| فایل | محتوا |
| --- | --- |
| `0001_tenancy` | academy_id روی جداول پایه، `academies`, `deliveries`, `sms_outbox` |
| `0002–0003` | قراردادها، رویدادها، فایل‌ها + مهر/امضای مدیر |
| `0004–0008` | ربات هر آموزشگاه، قطعه‌بندی فایل، لینک‌های در انتظار |
| `0009` | `payment_receipts`, `payment_transactions`, `payment_link_tokens` + `installments.payment_method` |
| `0010` | `payment_claims` (با عکس مدرک), `payment_events` + ستون‌های زمان‌بندی یادآوری |
| `0011` | `backups`, `backup_chunks`, `backup_runs` (مرحلهٔ ۷) |

## ۴. مراحل استقرار (وقتی مالک اجازه داد)

1. `npm test` (۲۰۸ تست) و `npx tsc --noEmit` و `npx wrangler deploy --dry-run` — همه سبز.
2. Secrets را با `wrangler secret put` تنظیم کنید (`API_SECRET_KEY`, `WEBHOOK_SECRET`, ...).
3. `npx wrangler d1 migrations apply academy-telegram-db --remote` — یک بار، به ترتیب ledger.
4. `npx wrangler deploy` و سپس set وب‌هوک هر ربات با همان secret.
5. بعد از استقرار: یک `/start` آزمایشی، یک منوی «اقساط من»، یک پشتیبان دستی از `/api/backup/run`
   و بررسی `GET /api/backup/status` (باید HEALTHY با `coveredTables` کامل باشد).

## ۵. محدودیت‌های شناخته‌شده (صادقانه، بدون ادعای اضافه)

1. **پشتیبان داخل همان D1 است** — در برابر از دست رفتن کل دیتابیس مستقل نیست؛ برای آن سناریو
   Time Travel رایگان (۷ روز) است. بازیابیِ دستی روی تولید هرگز به‌خودکار انجام نمی‌شود (runbook در `BACKUP_AND_MIGRATION_PLAN.md`).
2. **همگام‌سازی اقساط بدون LWW** — اگر اپ با نسخهٔ کهن بعد از تأیید سرور push کند، وضعیت پرداخت
   تا pull بعدی می‌تواند عقب برگردد (خودترمیم با pull `confirmed`؛ ریسک محدود به یک یادآوری اشتباه
   در همان بازه). تغییر این قراردادِ sync بدون تست با اپ واقعی عمداً انجام نشد — تصمیم با مالک.
3. **رسید آنلاین قسط اول** منتظر قرارداد نمی‌ماند (برخلاف رسید دستی/ادعا) — رفتار فعلی مستند و
   عمدی است؛ پرداخت درگاه یعنی ثبت‌نام انجام شده.
4. **یک کلید API سراسری** برای همهٔ آموزشگاه‌ها — با تک‌آموزشگاهی فعلی (`ACADEMY_IDS="default"`) درست است؛
   پیش از افزودن آموزشگاه دوم باید به کلید per-academy مهاجرت کرد (همچنین PK سراسری برخی جداول پایه).
5. **پنجرهٔ crash-after-send** — اگر Worker بین «ارسال موفق» و «ثبت وضعیت» بمیرد، پیام می‌تواند
   یک‌بار تکرار شود (تلگرام کلید idempotency ندارد)؛ دفتر deliveries پنجرهٔ overlap را می‌بندد و
   پس از ۱۰ دقیقه self-heal می‌کند.
6. **اندروید فقط در CI** — کامپایل/تست Kotlin در سندباکس ممکن نیست؛ `build-apk.yml` و `backend-ci.yml`
   آماده‌اند و باید اولین اجرای CI سبز شود.
7. **پیامک واقعی و درگاه واقعی غیرفعال‌اند** — پنل پیامکی آمادهٔ ورود کلید است (SMS.ir کامل، رایس‌اس‌ام‌اس منتظر مستندات رسمی؛ `SMS_PANELS.md`) و درگاه آنلاین با kill-switch مخفی است. ارسال/تراکنش واقعی فقط با اجازهٔ صریح مالک.
