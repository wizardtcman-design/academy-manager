# طرح استقرار ایمن Worker تولیدی (تغییرات، اثرها، روش بازگشت)

این سند قبل از هر استقرار تولیدی خوانده می‌شود. هیچ تغییری روی Worker تولیدی
بدون کلیک دستی «Run workflow» انجام نمی‌شود.

## ۱) وضعیت فعلی تولیدی (بررسی‌شده در تاریخ ۲۰۲۶-۱۰-۲۶)

- Worker `academy-manager1` زنده است (`/` پاسخ 200).
- مسیرهای `/api/bot/*` وجود دارند ولی نسخهٔ مستقر **قدیمی** است (قبل از
  مراحل ۳ تا ۹) و مشکلات[] تشخیصی ندارد.
- ربات تلگرام **وصل نیست** — تا امروز هیچ توکن رباتی به سیستم داده نشده است.
- Secretهای تولیدی (مثل `API_SECRET_KEY`) دست‌نخورده می‌مانند.

## ۲) این استقرار چه چیزی را تغییر می‌دهد؟

| مورد | تغییر | اثر |
|---|---|---|
| کد Worker | از نسخهٔ قدیمی به `main + dc31478` (مراحل ۱–۹ + تجربهٔ اتصال تازه) | قرارداد، اقساط، یادآورها، پیام‌ها، پشتیبان و پنل‌های جدید فعال می‌شوند |
| `/api/bot/status` | فیلد جدید `problems[]` به پاسخ اضافه می‌شود | افزودنی است؛ نسخه‌های قبلی اپ همچنان کار می‌کنند |
| دیتابیس D1 | مهاجرت‌های `0001..0011` اعمال می‌شوند | همه افزودنی‌اند (ستون/جدول جدید)؛ مهاجرت ۰۰۰۷ جدول را بازسازی می‌کند ولی **همهٔ ردیف‌ها کپی می‌شوند** |
| Cron | همان `* * * * *` قبلی | بدون تغییر |
| Secretها | — | با deploy دست نمی‌خورند |
| متغیرها | با Preflight محافظت می‌شوند | اگر مقدار تولیدی با `wrangler.toml` فرق داشته باشد، استقرار **متوقف** می‌شود (هرگز تغییر بی‌صدا نیست) |
| درگاه پرداخت آنلاین | `ONLINE_PAYMENTS_ENABLED = "false"` می‌ماند | همچنان مخفی و غیرفعال |
| پیامک واقعی | `SMS_PROVIDER = ""` می‌ماند | هیچ پیامک واقعی ارسال نمی‌شود |

## ۳) ریسک شناخته‌شده

- مهاجرت ۰۰۰۱ از `ALTER TABLE ADD COLUMN` استفاده می‌کند که در SQLite
  «تکرارپذیر» نیست؛ اگر دیتابیس تولیدی همین ستون‌ها را از قبل داشته باشد،
  مهاجرت خطا می‌دهد. در آن صورت **deploy کد متوقف می‌شود** (کد جدید مستقر
  نمی‌شود) و Worker قدیمی به کار عادی ادامه می‌دهد؛ با پشتیبان/Time Travel
  برمی‌گردیم و گزارش خطا را اصلاح می‌کنیم.

## ۴) روش بازگشت (Rollback)

1. **کد Worker**: در GitHub Actions لاگ نسخهٔ deployشده ثبت می‌شود؛ بازگشت با
   `npx wrangler rollback` (یا از داشبورد: Workers → academy-manager1 →
   Deployments → Rollback). نسخهٔ قبلی بلافاصله جایگزین می‌شود.
2. **دیتابیس D1**: قبل از هر تغییر، یک فایل پشتیبان SQL به‌عنوان آرتیفکت
   همان اجرای workflow ذخیره می‌شود (نگهداری ۳۰ روز). بازگشت نقطه‌زمانی هم
   همیشه موجود است: داشبورد → D1 → Time Travel.
3. **بازگردانی از پشتیبان SQL**: `npx wrangler d1 execute <DB> --remote --file=backup.sql`
   (فقط با تأیید مالک و بعد از بررسی).

## ۵) پیش‌نیازهای امن (یک‌بار)

1. **Secretهای GitHub** — صفحهٔ
   `github.com/wizardtcman-design/academy-manager/settings/secrets/actions`
   → «New repository secret»:
   - `CLOUDFLARE_API_TOKEN` — توکنی که خودتان در
     `dash.cloudflare.com/profile/api-tokens` با «Create Custom Token»
     می‌سازید؛ فقط دو مجوز لازم دارد:
     **Account → Workers Scripts → Edit** و **Account → D1 → Edit**
     (محدود به همین حساب). این توکن فقط داخل GitHub ذخیره می‌شود.
   - `CLOUDFLARE_ACCOUNT_ID` — از داشبورد Cloudflare (سمت راست صفحهٔ
     Workers یا صفحهٔ اصلی حساب).
2. هیچ‌کدام از این مقادیر در چت، کد یا APK قرار نمی‌گیرند.

## ۶) چگونه استقرار را اجرا کنیم؟

1. GitHub → مخزن → تب **Actions** →
   **«Deploy Worker (production) — manual only»** → **Run workflow**.
2. خودِ همین کلیک = تأیید جداگانهٔ استقرار تولیدی.
3. اگر Preflight توقف کرد، گزارش فارسیِ همان لاگ می‌گوید دقیقاً کدام خط
   `wrangler.toml` را باید با مقدار تولیدی هم‌تراز کنید.
