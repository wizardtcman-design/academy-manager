# مرحله ۷ — پشتیبان‌گیری خودکار سرور، سلامت مالی و گزارش درآمد

> **وضعیت: فقط محیط توسعه — هیچ تغییری روی Production اعمال نشده است.**
> این سند معماری، محدودیت‌های رایگان و راهنمای بازیابی را مستند می‌کند.

---

## ۱. پشتیبان‌گیری خودکار روزانه (سمت سرور)

### معماری و انتخاب آزادانهٔ رایگان
- **محل ذخیره:** همان پایگاه‌دادهٔ D1 خود آموزشگاه (جدول‌های `backups` + `backup_chunks` — مهاجرت ۰۰۰۹، **فقط محلی**، روی D1 تولیدی اجرا نشده).
- **چرا R2 یا سرویس دیگر نه؟** R2 روی این حساب Cloudflare فعال نیست (خطای API 10042) و فعال‌کردن هر سرویس جدید/پولی در این مرحله ممنوع است. D1 رایگان تا **۵ گیگابایت** فضا می‌دهد و نگه‌داری ۷ نسخه از پایگاه‌دادهٔ فعلی (~۲۱ مگابایت، فشرده حدود ~۱۰ مگابایت در روز) به‌مراتب زیر سقف رایگان است.
- **بازیابی فاجعهٔ کامل D1:** قابلیت **Time Travel** خود Cloudflare (رایگان، ۳۰ روز نقطه‌زمانی) لایهٔ بازیابی کلی است؛ پشتیبان داخل D1 محافظ **خرابی منطقی** است (حذف اشتباهی، نوشتن غلط، خرابی ردیف).
- محاسبهٔ فضا: هر نسخه ≈ ۵–۱۵ مگابایت فشرده × ۷ نسخه ≈ **زیر ۱۵۰ مگابایت** — حتی با رشد ۱۰ برابری قراردادها هم رایگان می‌ماند.

### جریان کاری هر نسخه (Verify-before-replace)
1. `cron` هر دقیقه اجرا می‌شود؛ **یک بار در شبانه‌روز تهران** (آفست ثابت ‎+03:30‎ — ایران از ۱۴۰۱ ساعت تابستانی ندارد) برای هر آموزشگاه `runBackup(AUTO)` را صدا می‌زند.
2. خروجی JSON همهٔ جدول‌های ضروریِ همان آموزشگاه ساخته می‌شود: `students, installments, financial_summaries, reminders, message_logs, deliveries, sms_outbox, pending_students, contracts, contract_events, contract_deliveries, contract_files (با بایت‌های فایل), contract_file_chunks, academy_settings` + ردیف `academies`.
3. فشرده‌سازی gzip و ذخیرهٔ تکه‌تکه (تکه‌های ۷۶۸ کیلوبایتی — سقف پارامتر D1 یک مگابایت است، همان الگوی `contract_file_chunks`).
4. **صحت‌سنجی قبل از جایگزینی:** خواندن دوبارهٔ تکه‌ها → تطبیق SHA-256 → بازکردن gzip → تحلیل JSON → مقایسهٔ شمارش ردیف‌ها و جمع‌های مالی (اقساط/پرداخت/بدهی/شهریه) با دادهٔ زنده → بازسازی و هش فایل‌های قرارداد (هم inline و هم chunked).
5. فقط بعد از `HEALTHY` شدن نسخهٔ جدید، نسخه‌های قدیمی‌تر هرس می‌شوند (نگه‌داری آخرین ۷ نسخهٔ سالم + ۳ نسخهٔ خراب اخیر برای بررسی). **اگر نسخهٔ جدید خراب باشد، هیچ نسخهٔ سالم قبلی حذف نمی‌شود** (تست‌شده).
6. نشانگر روز فقط بعد از نسخهٔ سالم ثبت می‌شود؛ پس شکست → دقیقهٔ بعد cron دوباره تلاش می‌کند.

### مدیریت و مشاهده
- `GET /api/backup/status` — آخرین تلاش، نتیجه، خطا، تعداد نسخه‌های سالم، اندازه (فقط متادیتا؛ **هیچ‌وقت محتوای پشتیبان یا توکن از API بیرون نمی‌آید**).
- `POST /api/backup/run` — اجرای دستی/تلاش مجدد (همان مسیر صحت‌سنجی).
- رابط کاربری اپ: بخش «ربات → تنظیمات → پشتیبان‌گیری خودکار سرور» (کارت `BotBackupSection`) — زمان آخرین نسخهٔ سالم، تعداد نسخه‌ها، خطای آخرین تلاش، دکمهٔ اجرای فوری.
- متغیرهای تنظیمی (wrangler.toml): `BACKUP_RETENTION_DAYS=7`، `BACKUP_MAX_BYTES=26214400`، `BACKUP_INCLUDE_FILES=true`.
  - اگر فشرده از ۲۵ مگابایت گذشت، نسخهٔ بعدی فقط متادیتا + هش فایل‌ها را ذخیره می‌کند و در UI صریحاً «فایل‌ها ذخیره نشد» نمایش داده می‌شود — هیچ‌وقت پوششِ غیرواقعی ادعا نمی‌شود.

## ۲. بررسی سلامت مالی

### سمت سرور (`GET /api/finance/health`) — فقط گزارش، بدون تغییر داده
- بررسی حسابی اقساط: `remaining == amount − paid`، عدم پرداخت بیش از مبلغ، منفی نبودن مبالغ، هم‌خوانی پرچم `is_paid`.
- مقایسهٔ خلاصهٔ مالی هر هنرجو (`financial_summaries`) با جمع اقساط خودش — کشف همگام‌سازی ناتمام.
- محاسبهٔ **اقساط معوق از دادهٔ خام** (سررسید گذشته + پرداخت‌نشده، منطقهٔ زمانی تهران) به‌جای اتکا به رشتهٔ وضعیتِ احتمالاً کهنه.
- خروجی شامل `totals` (شهریه/پرداخت واقعی/بدهی/معوق) برای **مغایرت‌یابی سه‌طرفهٔ Android ↔ Worker ↔ D1**.

### سمت اپلیکیشن (`FinanceHealthChecker` — دکمهٔ «بررسی سلامت مالی» در گزارش‌ها)
- تطبیق دفتر پرداخت واقعی (بدون تراکنش‌های لغوشده) با `paidAmount` هر قسط.
- کشف **کد تراکنش تکراری** (خطا) و **پرداخت دوعددی مشکوک در فاصلهٔ زیر ۲ دقیقه** (هشدار، با راهنمای «اصلاح/لغو تراکنش»).
- برگشت وجهِ بیشتر از پرداخت واقعی هنرجو = خطا.
- **غیرمخرب:** فقط لیست ورودی می‌گیرد و فقط گزارش برمی‌گرداند؛ بدون تأیید مالک هیچ سابقهٔ مالی تغییر نمی‌کند.

> ثبت پرداخت تکراری از قبل در `recordPayment` جلوگیری می‌شود (بازخوانی دفتر پرداخت قبل از ثبت، ردّ مبلغ بیش از مانده) — مرحلهٔ ۷ این رفتار را تست‌شده نگه می‌دارد.

## ۳. گزارش خودکار درآمد (اپلیکیشن)

- موتور محاسبه: `ReportCalculator` (خالصِ JVM، تست‌شده) — **درآمد فقط از پرداخت‌های واقعی ثبت‌شده و لغونشده**؛ شهریهٔ تعیین‌شده و اقساط پرداخت‌نشده هرگز «درآمد وصول‌شده» حساب نمی‌شوند.
- گزارش ماه دلخواه (۱۲ ماه شمسی) و سال دلخواه (۵ سال اخیر) + تفکیک ۱۲ ماه سال با برگشت وجه.
- تفکیک بر اساس **دوره**، **هنرجو** و **روش پرداخت** (کارت به کارت/کارتخوان/نقدی/واریز بانکی/سایر).
- کارت جداگانه: شهریهٔ کل / وصول واقعی / بدهی باقی‌مانده / تعداد و مبلغ اقساط معوق (از دادهٔ خام، خارج‌شدن اقساط لغوشده).
- فیلتر روش پرداخت و دوره + انتخاب ماه/سال.
- **خروجی CSV با BOM** (قابل باز کردن مستقیم در Excel، رایگان، بدون سرویس خارجی) از طریق FileProvider موجود.
- رابط فارسی، راست‌چین و موبایل‌محور (کارت‌های موجود حفظ و گسترش یافته‌اند).

## ۴. آزمون بازیابی (فقط محیط آزمایشی)

`test/stage7-backup-finance.test.ts` → «recovery test (sandbox)»:
- پشتیبان از دیتابیسِ داده‌دار گرفته می‌شود، سپس در یک **D1 تازه (in-memory)** با اجرای همهٔ مهاجرت‌ها بازگردانی می‌شود.
- بعد از بازیابی بررسی می‌شود: شمارش ردیف‌ها، جمع مبالغ اقساط، بی‌سروته نبودن رابطهٔ هنرجو↔قسط، هش SHA-256 فایل‌های قرارداد (inline و chunked)، بقای تنظیمات آموزشگاه و **نرفتن دادهٔ آموزشگاه دیگر**.
- هیچ مسیر HTTP بازیابی‌کننده‌ای وجود ندارد؛ `restoreBundleForTests` فقط برای تست در دسترس است. بازیابی واقعی نیازمند تأیید مالک و اجرای دستی طبق همین سند است.

## ۶. محدودیت‌های رایگان و موارد تکمیل‌نشده

1. **R2 غیرفعال است** — پشتیبان داخل D1 نگه‌داری می‌شود؛ اگر مالک بعداً R2 رایگان را در داشبورد فعال کند، می‌توان مقصد پشتیبان را به R2 برد (سقف رایگان ۱۰ گیگابایت) بدون تغییر در الگوریتم صحت‌سنجی.
2. **بازیابی دستیِ واقعی روی تولید انجام نشد** (و نباید انجام شود) — بازیابی آزمایشی فقط روی دیتابیس تست اجرا شد؛ اجرای بازیابی روی تولید نیازمند دستور مالک است.
3. **مهاجرت ۰۰۰۹ روی D1 تولیدی اجرا نشده** — تا وقتی اجرا نشود، endpointهای پشتیبان خطای «جدول پیدا نشد» می‌دهند و cron پشتیبان با شکست ثبت‌شده رد می‌شود ( reminders را مختل نمی‌کند).
4. **کامپایل اندروید در سندباکس انجام نشد** — تغییرات Kotlin باید در CI (مرحلهٔ ۹) تأیید شوند؛ منطق مالی/گزارش/پشتیبان به‌صورت خالصِ JVM نوشته شده تا تست‌پذیر باشد.
5. **نگه‌داری بیش از ۷ نسخه یا ذخیرهٔ مستقل خارج از D1 به سرویس/فضای بیشتر نیاز دارد** — فعال نشده؛ سقف رایگان فعلی مستند شد.
6. SMS/درگاه پرداخت همچنان غیرفعال‌اند (طبق مراحل قبل) و در این مرحله تغییری نکرده‌اند.

## ۷. ممنوعیت‌های رعایت‌شده

هیچ سرویس پولی/اشتراک جدید، هیچ انتشار روی سرور واقعی، هیچ مهاجرت روی D1 تولیدی، هیچ حذف داده، هیچ پیام واقعی و هیچ تغییر تنظیمات عملیاتی انجام نشده است. همهٔ تغییرات روی شاخهٔ `sec/stage7-backup-finance` و فقط محیط توسعه است.
