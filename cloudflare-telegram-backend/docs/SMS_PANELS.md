# پنل‌های پیامکی — مرحله ۹ + معماری توسعه‌پذیر (SMS Panels)

> وضعیت کلی: **آمادهٔ ورود کلید توسط مالک** — هیچ پیامک واقعی تا وارد‌شدن
> اطلاعات واقعی و اجازهٔ صریح مالک ارسال نمی‌شود. کل این مرحله فقط با
> mock تست شده است («آزمایش‌شده با mock»)، نه با API واقعی.

این سند نتیجهٔ بررسی مستندات رسمی دو ارائه‌دهنده، معماری پیاده‌سازی‌شده،
محل امن وارد‌کردن کلیدها و وضعیت واقعی هر قابلیت است.

**نتیجهٔ صریح:** رایس‌اس‌ام‌اس **هیچ مستندات عمومی وب‌سرویس منتشر نکرده
است**. تبلیغ پنل‌ها فقط می‌گوید «وب سرویس ارسال پیامک» جزو امکانات است.
طبق دستور مأموریت، **هیچ endpoint یا پارامتری حدس زده یا جعل نشده** —
اسلات ارائه‌دهنده با وضعیت صادقانه «در انتظار مستندات» ثبت شده و
آداپتور آن تا دریافت مستندات واقعی، ارسال و آزمایش اتصال را با پیام
شفاف رد می‌کند. **هیچ فراخوانی شبکه‌ای برای این پنل انجام نمی‌شود.**

## ۲. مشخصات واقعی API — SMS.ir (مبنای پیاده‌سازی)

- **Base URL:** `https://api.sms.ir/v1`
- **احراز هویت:** هدر `X-API-KEY` (کلید از پنل ← برنامه‌نویسان ← کلیدهای API)
- **ارسال متنی (bulk):** `POST /v1/send/bulk`
  ```json
  { "lineNumber": 3000xxxxxxxxxx, "messageText": "...", "mobiles": ["09xxxxxxxxx"] }
  ```
  پاسخ موفق: `{"status":1,"message":"...","data":{"packId":"<guid>","messageIds":[...],"cost":<decimal>}}`
  (حداکثر ۱۰۰ گیرنده در هر درخواست — سیستم ما همیشه ۱ گیرنده می‌فرستد)
- **اعتبارسنجی پاسخ:** `status:1` = موفق؛ سایر کدها از جدول رسمی به کدهای
  استاندارد سیستم نگاشت شده‌اند (`SmsErrorCode` — ۱۰/۱۱/۱۲/۱۳/۱۴ →
  `UNAUTHENTICATED`، ۱۰۲ → `NO_CREDIT`، ۱۰۱/۱۲۳ → `INVALID_LINE`،
  ۱۰۴ → `INVALID_MOBILE`، ۲۰ → `RATE_LIMITED`، ۰/۱۰۳/۱۰۵/۱۱۵/۱۱۷ → `REJECTED`،
  کد مستندنشده → `PROVIDER_ERROR`).
- **معنای دقیق messageIds (بازبینی ۲۰۲۶-۱۰-۲۶، طبق صفحهٔ رسمی):**
  «مقادیر آرایهٔ MessageIds می‌تواند شامل مقادیر id متناظر آن، Null و یا
  صفر باشد. مقدار صفر به این معناست که شمارهٔ متناظر در لیست سیاه است.
  مقدار Null به این معناست که شمارهٔ متناظر غلط یا متن بیش از حد است.» —
  پیاده‌سازی هر دو را **FAILED** گزارش می‌کند (هرگز SENT جعلی).
- **آزمایش اتصال (رایگان):** `GET /v1/credit` → `{"status":1,"data":165.3}`
  — بدون هیچ هزینه و بدون ارسال پیامک؛ همان چیزی که دکمهٔ «آزمایش اتصال» صدا می‌زند.
- **گزارش وضعیت ارسال:** `GET /v1/send/{messageId}` با فیلد `deliveryState`
  (Nullable Byte) و `deliveryDateTime` (UnixTime). صفحهٔ رسمی REST مقدارها را
  توضیح نمی‌دهد؛ بنابراین مقدار **خامِ** دلیوری بدون تفسیر گزارش می‌شود
  (endpoint مدیریتی `GET /api/messaging/sms/delivery?ledgerId=…`؛ null =
  «پنل هنوز گزارش نکرده»). شناسهٔ ارسال از ابتدا در دفتر deliveries ثبت می‌شود.
- **ارسال قالبی (خط خدماتی):** `POST /v1/send/verify` با
  `{mobile, templateId, parameters:[{name,value}]}` → `data:{messageId,cost}`
  — **حالا در لایهٔ مشترک پیاده‌سازی شده** (`sendSmsTemplate` + endpoint
  مدیریتی `POST /api/messaging/sms/send-template`، idempotent با clientMsgId
  و همان ضدتکرار). خط خدماتی نیاز به تبدیل رسمی خط دارد
  (شرایط در sms.ir/خدماتی-سازی-خطوط).
- **محدودیت‌ها:** کلید می‌تواند به IP محدود شود (کد ۱۲)؛ خط خدماتی فقط
  برای اشخاص حقوقی؛ ارسال bulk تا تبدیل خدماتی به شماره‌های سیاهه نمی‌رسد.
- **Sandbox:** پنل اجازهٔ ساخت کلید sandbox می‌دهد (همان URLها، بدون
  ارسال واقعی) — برای آزمایش اولیهٔ مالک بدون هزینه توصیه می‌شود.

### رایس‌اس‌ام‌اس — مشخصات
**UNVERIFIED — عمومی نیست.** فیلدهای فرم (کلید وب‌سرویس + خط) آماده است
تا مالک پس از دسترسی به مستندات داخل پنل، مشخصات واقعی را تأیید کند؛
در آن نقطه فقط آداپتور HTTP این فایل (`cloudflare-telegram-backend/src/sms.ts`)
تکمیل می‌شود و به منطق کسب‌وکار دست نخواهد خورد.

## ۳. معماری پیاده‌سازی‌شده

```
src/sms.ts                      ← قرارداد رسمی SmsProviderAdapter + رجیستری + آداپتورها + ارسال یکتا
types استاندارد خطا            ← SmsErrorCode (نگاشت خطاهای پنل به واژگان سیستم)
sendSmsTemplate()               ← ارسال قالبی مستندشده + همان ضدتکرار
querySmsDeliveryStatus()        ← گزارش دلیوری (مقدار خام، بدون تفسیر)
reminders.ts / receipts.ts      ← یادآوری‌ها + رسیدها (سیاست کانال هر رویداد)
handlers/webhook.ts             ← کپی SMS برای CLAIM_ACK / RECEIPT_REJECTED /
                                  CONNECT_WELCOME / CONTRACT_DELIVERED
handlers/contracts-api.ts       ← پیامک خوش‌آمد (قبلاً DISABLED بود)
handlers/messaging-api.ts       ← ارسال دستی + تنظیمات پنل + send-template + delivery
handlers/api.ts                 ← کلیدهای پنل/پشتیبان در /api/sync/settings رزرو شده‌اند
gateway.ts                      ← قرارداد درگاه: link/verify الزامی + status/cancel/refund اختیاری
app: SmsPanelSection.kt         ← UI تنظیمات (تب «د) پنل پیامکی»)
```

**قاعدهٔ واحد:** هیچ بخشی از کسب‌وکار مستقیماً با پنل/درگاه حرف نمی‌زند؛
همه از `resolveSmsProvider()` + `sendSmsText()`/`sendSmsTemplate()` عبور
می‌کنند. راهنمای گام‌به‌گام افزودن پنل یا درگاه جدید:
**`docs/PROVIDER_DEVELOPMENT.md`**.

### ذخیره‌سازی (بدون migration جدید)
در همان جدول namespaced `academy_settings` (D1) هر آموزشگاه (سازوکار امن موجود —
مثل `gateway_api_key`):
- `sms_provider` = `` | `smsir` | `rysesms`
- `smsir_api_key`، `smsir_line`
- `rysesms_api_key`، `rysesms_line`

قوانین امنیتی (تست‌شده):
- مقدار کلید **هرگز** در پاسخ API برنمی‌گردد (فقط `hasValue`)، هرگز لاگ
  نمی‌شود و هرگز داخل متن خطا نیست.
- ذخیرهٔ تنظیمات با فیلدهای ناقص رد می‌شود (فعال‌سازی ناقص غیرممکن است).
- فیلد secret خالی در PUT = «قبلی بماند»؛ تغییر پنل، فیلدهای پنل دیگر و
  سوابق پیامک را پاک نمی‌کند.
- **مسیر همگام‌سازی اپ (`/api/sync/settings`) نمی‌تواند این کلیدها را بنویسد:**
  `sms_provider`، `smsir_*`، `rysesms_*` (و `backup:*`) رزرو هستند و پوشِش
  all-or-nothing رد می‌شود — پیکربندی پنل فقط از API مدیریتی تغییر می‌کند
  (تست‌شده).
- **Secret اختیاری Cloudflare:** `wrangler secret put SMSIR_API_KEY` —
  اگر تنظیم شود بر مقدار ذخیره‌شدهٔ D1 اولویت دارد (برای کسانی که ترجیح
  می‌دهند کلید در کد/دیتابیس نباشد).

### سیاست کانال و جلوگیری از تکرار
- کانال مجاز هر رویداد همان تنظیمات قبلی است (`telegram | sms | both`)؛
  وقتی کانال رویداد `telegram` است **هیچ SMS ارسال نمی‌شود** و ردیف
  صادقانهٔ `SKIPPED / sms_channel_disabled_by_settings` نوشته می‌شود.
- «فقط پیامک» حالا واقعاً پیامک می‌فرستد (قبلاً هیچ چیز ارسال نمی‌شد).
- قبل از هر فراخوانی HTTP، slot در دفتر `deliveries` (کانال `sms`) رزرو
  می‌شود — تلاش مجدد، کرش یا اجرای هم‌پوشان cron هرگز پیامک دوباره
  نمی‌فرستد (تست‌شده).
- شمارهٔ موبایل قبل از هر فراخوانی نرمال‌سازی می‌شود (۰۹۱۲…/۹۸…/‎+۹۸/‎۰۰۹۸/
  ارقام فارسی)؛ شمارهٔ نامعتبر قبل از رسیدن به پنل رد می‌شود.
- Timeout پنل ۱۲ ثانیه؛ خطای شبکه/timeout پیام فارسی صادقانه می‌دهد و
  هیچ‌وقت crash یا پیامِ «موفقِ جعلی» نمی‌سازد.

## ۴. محل وارد‌کردن کلیدها (گام‌به‌گام برای مالک)

**SMS.ir:**
1. وارد پنل sms.ir شوید ← برنامه‌نویسان ← کلیدهای API ← کلید بسازید
   (برای آزمایش اولیه، کلید sandbox).
2. در اپ آموزشگاه: تنظیمات ← پیام‌ها ← تب «د) پنل پیامکی» ← انتخاب
   «SMS.ir» ← «کلید API (X-API-KEY)» و «شماره خط ارسال» را وارد کنید ← ذخیره.
3. دکمهٔ «آزمایش اتصال» را بزنید — باید اعتبار پنل را نشان دهد.
   *هیچ پیامکی ارسال نمی‌شود.*
4. اختیاری: `wrangler secret put SMSIR_API_KEY` (Secret ابری با اولویت بالاتر).
5. وقتی اجازهٔ ارسال واقعی را دادید: کانال رویدادهای دلخواه را در تب
   «ج) تنظیمات سرور ربات» روی «پیامک» یا «هر دو» بگذارید.

**رایس‌اس‌ام‌اس:** پنل ← بخش وب‌سرویس (پس از ورود) ← مستندات و کلید را
بگیرید؛ تا انتشار مستندات رسمی، اتصال این پنل صادقانه غیرفعال می‌ماند.

> **تا وارد‌کردن اطلاعات واقعی توسط شما، هیچ پیامکی — حتی آزمایشی —
> ارسال نمی‌شود.** دکمهٔ آزمایش اتصال فقط endpoint رایگان اعتبار را
> می‌خواند و دکمهٔ «ارسال آزمایشی واقعی» عمداً وجود ندارد.

## ۵. وضعیت واقعی قابلیت‌ها

| قابلیت | وضعیت |
|---|---|
| آداپتور SMS.ir بر اساس مستندات رسمی | ✅ پیاده‌سازی + تست‌های mock (قرارداد URL/هدر/body، نگاشت کامل کدهای خطا به `SmsErrorCode`، معنای رسمی messageIds، timeout، اعتبار) |
| اتصال SMS.ir به یادآوری/رسید/رویدادها/خوش‌آمد/ارسال دستی | ✅ پیاده‌سازی + تست mock (سیاست کانال، ضدتکرار، idempotency) |
| آزمایش اتصال بدون هزینه (credit) | ✅ تست mock — **نیازمند آزمایش واقعی با کلید شما** |
| ارسال قالبی (قالب خدماتی، `/v1/send/verify`) | ✅ پیاده‌سازی در لایهٔ مشترک + endpoint مدیریتی idempotent + تست mock — **نیازمند آزمایش واقعی با کلید و قالب ثبت‌شده** |
| گزارش دلیوری (`GET /v1/send/{id}`) | ✅ پیاده‌سازی (مقدار خام بدون تفسیر — صفحهٔ رسمی REST legend منتشر نکرده) + endpoint مدیریتی + تست mock — **نیازمند آزمایش واقعی** |
| ارسال واقعی SMS.ir | ⏳ «نیازمند ورود کلید + اجازهٔ صریح مالک» — توسط mock پوشش داده شده، با API واقعی آزمایش نشده |
| رایس‌اس‌ام‌اس | ⚠️ اسلات + فرم آماده؛ **آداپتور ارسال مسدود تا انتشار مستندات رسمی** (بازبینی ۲۰۲۶-۱۰-۲۶: سایت همچنان WAF 403؛ هیچ مستندات عمومی) |
| مخفی‌بودن کامل درگاه پرداخت آنلاین | ✅ تست‌شده (gateway-hidden.test.ts + provider-architecture.test.ts) |
| ادامهٔ کارت‌به‌کارت + تأیید مدیر | ✅ تست‌شده (همان فایل‌ها) |
| قرارداد توسعه‌پذیر درگاه (status/cancel/refund) | ✅ قرارداد + رجیستری + تست «فعال‌سازی تصادفی غیرممکن» — هیچ مسیر API فعلی این قابلیت‌ها را صدا نمی‌زند |

شمارش تست‌ها در تاریخ بازبینی: **۲۲۰/۲۲۰ سبز** (۲۰۸ قبلی + ۱۲ تست معماری
ارائه‌دهنده‌ها) + `tsc --noEmit` تمیز + `wrangler deploy --dry-run` موفق.
