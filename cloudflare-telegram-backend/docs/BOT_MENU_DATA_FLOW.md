# جریان دادهٔ منوی ربات تلگرام (مرحله ۳)

این سند دقیقاً توضیح می‌دهد هر یک از **۶ دکمهٔ منوی هنرجو** در ربات از کدام داده تغذیه می‌شود، داده از کدام مسیر به سرور می‌رسد و چه جداسازی‌هایی اعمال می‌شود. هیچ‌کدام از این دکمه‌ها دادهٔ ساختگی نشان نمی‌دهند؛ همه از ردیف‌های D1 می‌خوانند که خودِ اپلیکیشن آموزشگاه از طریق مسیرهای احرازهویت‌شده push کرده است.

## نقشهٔ دکمه ← داده

| دکمه | منبع داده (D1) | مسیر همگام‌سازی از اپ | نکته |
|---|---|---|---|
| 💰 وضعیت مالی | `financial_summaries` | `/api/sync/financials` | کل شهریه، پرداختی، مانده، خلاصه دوره‌ها |
| 📅 اقساط من | `installments` | `/api/sync/installments` | همهٔ اقساط با وضعیت پرداخت‌شده / در انتظار / سررسیدگذشته (محاسبهٔ دیرکرد در سرور) |
| 🧾 رسیدهای من | `installments` (فقط `is_paid = 1`) | `/api/sync/installments` | هر قسط پرداخت‌شده = یک رسید: مبلغ پرداخت‌شده، تاریخ پرداخت شمسی، دوره. فاکتور تفصیلی در اپ می‌ماند |
| 📄 قرارداد من | `contracts` + `contract_files` | (جریان قرارداد مرحله ۲) | نسخهٔ SIGNED → ارسال فایل واقعی PDF با `sendDocument` + ثبت رویداد `PDF_SENT`; ISSUED → راهنمای امضا؛ بدون قرارداد → پیام صادقانه |
| 📞 تماس با آموزشگاه | `academy_settings` | `/api/sync/settings` | نام/تلفن/نشانی/واحد پول **خودِ آموزشگاه**؛ قبل از اولین push مقادیر پیش‌فرض |
| 🔄 بروزرسانی اطلاعات | `students` + `financial_summaries` + `installments` | همهٔ مسیرهای بالا | بازخوانی کامل ردیف‌های خود هنرجو + شمارش اقساط |

## اتصال امن هنرجو (پیش‌نیاز همهٔ دکمه‌ها)

- اپ با `/api/generate-link` یک **توکن یک‌بارمصرف** می‌سازد؛ سرور فقط SHA-256 آن را روی ردیف هنرجو نگه می‌دارد و توکن خام فقط داخل لینک `https://t.me/<bot>?start=<token>` می‌ماند.
- هنرجو `/start <token>` را می‌زند؛ سرور هش را بررسی می‌کند، چت را **فقط به همان هنرجو** متصل می‌کند و توکن را می‌سوزاند. شناسهٔ خام هنرجو هرگز پذیرفته نمی‌شود (پاسخ خنثی، بدون افشای وجود).
- هر دکمه‌ای قبل از اتصال → پیام «حساب شما متصل نشده است» بدون هیچ دادهٔ مالی.

## جداسازی آموزشگاه‌ها و هنرجوها

1. **چت → هنرجو:** `SELECT * FROM students WHERE telegram_chat_id = ? AND academy_id = ?` — یک چت فقط در آموزشگاهِ خودش معنا دارد (وبهوک هر آموزشگاه `/webhook/<academyId>` با توکن و secret اختصاصی همان آموزشگاه).
2. **همهٔ خواندنی‌ها scoped:** اقساط/خلاصهٔ مالی/قرارداد/یادآوری‌ها همه با `student_id` هنرجوی همان چت و `academy_id` همان وبهوک خوانده می‌شوند.
3. **کلیدهای KV مستأجر-scoped:** `chat:<academyId>:<chatId>`.
4. **تنظیمات per-academy بدون تغییر schema:** ردیف‌های `academy_settings` با کلید namespaced `<academyId>:<key>` نوشته می‌شوند؛ خواندن اول کلید namespaced و در نبود آن ردیف قدیمی بدون پیشوند (سازگاری با داده‌های قبل از چند-مستأجری) را می‌خواند. نوشتن همیشه namespaced است؛ پس آموزشگاه A هرگز تنظیمات B را بازنویسی یا نمی‌خواند. **نیازی به مهاجرت جدید نیست.**
5. **تنظیمات حساس هرگز sync نمی‌شوند:** توکن ربات، کلید API سرور، کلید SMS، PIN قفل اپ فقط روی گوشی می‌مانند؛ فقط نام/تلفن/نشانی/واحد پول push می‌شوند.

## تست‌ها

`test/bot-menu.test.ts` هر ۶ دکمه را **از طریق وبهوک واقعی و دادهٔ push‌شده از مسیرهای API واقعی اپ** پوشش می‌دهد (۱۴ تست): اعداد مالی واقعی، فهرست اقساط با دیرکرد، رسیدهای تفصیلی فقط از اقساط پرداخت‌شده، ارسال فایل واقعی PDF قرارداد با ثبت `PDF_SENT`، نمایش اطلاعات تماس push‌شده به‌جای مقادیر پیش‌فرض، شمارش‌های بروزرسانی، ردّ چت بدون اتصال برای هر ۶ دکمه، سازگاری ردیف legacy تنظیمات، و عدم نشت تنظیمات بین دو آموزشگاه.

## محدودیت‌های عملیاتی (تا اجرای واقعی محیط، صرفاً تأییدنشده است)

- ارسال واقعی پیام/فایل به یک چت واقعی تلگرام هنوز **عملیاتی تست نشده** (بدون توکن واقعی و اکانت تست، طبق سیاست امن انجام نشد)؛ منطق سمت سرور با Mock کامل پوشش داده شده است.
- نمایش رسیدهای تفصیلیِ غیر-قسطی (مثلاً پرداخت‌های دستی) در ربات نیازمند sync جدول پرداخت‌هاست که فعلاً در اپ push نمی‌شود؛ رسیدهای ربات از اقساط پرداخت‌شده ساخته می‌شود.
